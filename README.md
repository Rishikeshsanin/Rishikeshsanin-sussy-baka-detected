# Sussy Baka Detected

**Think of someone. Don't snitch. Let the detector cook.**

Sussy Baka Detected (SBD) is an Akinator-inspired guessing game for real people and fictional characters. The player answers **Yes**, **No**, **Probably**, **Probably not**, or **Don't know** while a hybrid deduction engine narrows the suspect pool and tries to identify the person in roughly twenty questions.

The meme personality is intentional. The deduction system underneath it is not a meme.

> SBD is an independent project with original branding and implementation. It is not affiliated with Akinator.

## What changed from the failed V1

The legacy prototype treated an LLM as almost the entire deduction engine: it invented the next question, candidate shortlist, and confidence value. That made a polished demo but an unreliable game.

The current architecture separates those jobs:

- a bundled hot pool handles common guesses with zero external lookup latency;
- every structured answer updates candidate likelihoods;
- the next local question is selected by expected information gain;
- Wikipedia/Wikidata can inject **current, verified entities at runtime** once enough clues exist;
- recent Wikipedia pageviews and search rank contribute a popularity prior;
- incomplete live records use open-world scoring, so missing metadata means **unknown**, not automatically **no**;
- Gemini is a semantic/long-tail assistant rather than the database or confidence calculator;
- rejected guesses are removed from the candidate distribution;
- upstream Gemini/Wikimedia failures do not end the round while useful structured questions remain.

The exact original prototype is preserved on the [`legacy-v1`](../../tree/legacy-v1) branch.

## Current features

- Adaptive game length: easy cases can finish early; difficult cases can continue up to a 30-question safety ceiling.
- Five answer strengths that preserve uncertainty instead of forcing every clue into a boolean.
- Bayesian-style weighted candidate ranking.
- Entropy/information-gain question selection.
- Global geography, profession, sport, entertainment, franchise, era, and role questions.
- **Live Wikipedia discovery** for people/characters outside the bundled hot pool.
- **Wikidata verification/enrichment** for discovered entities.
- **30-day Wikipedia pageviews** + search order used as a popularity signal.
- Bounded live-lookup timeouts and a small in-memory discovery cache.
- Gemini 3.6 Flash with low-thinking latency tuning and Flash-Lite fallback.
- Server-side confidence calibration for LLM guesses.
- Wrong-guess recovery without restarting the game.
- AI-outage continuation: provider failures become more questions instead of a dead-end error screen.
- Duplicate-question and rejected-guess protection.
- Undo, restart, answer history, retry, win, and give-up flows.
- Versioned local persistence so active games survive refreshes safely.
- Contextual meme reactions based on game state instead of random meme spam.
- Responsive mobile/desktop layout, keyboard controls, focus states, reduced-motion support, and semantic live status.
- Dynamic favicon and social preview generated by Next.js.
- CI quality gate for typecheck, tests, lint, production build, and runtime smoke test.

## Knowledge Engine

SBD does **not** try to keep every famous person hand-written in source code.

```text
Player answers
    |
    v
Bundled hot pool
    |  probability + information gain
    |
    +-------- enough structured clues? --------+
    |                                           |
    | no                                        | yes
    v                                           v
Ask next local question                 Build search plan
                                                |
                                                v
                                      English Wikipedia search
                                                |
                              page intro + Wikidata item + pageviews
                                                |
                                                v
                                      Wikidata verification
                                                |
                               human/type + gender + country + dates
                                                |
                                                v
                                 Live candidate enrichment/ranking
                                                |
                           merge with hot pool + recompute probabilities
                                                |
                                                v
                                  ask / guess / semantic AI fallback
```

### Why this matters

A newly popular athlete, actor, creator, politician, musician, or character does not need a code release just to become discoverable. Once the user's answers form a useful search fingerprint, current Wikimedia knowledge can add candidates to the round.

The bundled pool still exists because it is faster and more reliable for very common guesses. Live discovery expands coverage instead of replacing the deterministic core.

### Popularity

Live candidates receive a bounded prior using:

- recent English Wikipedia pageviews;
- Wikipedia search position;
- structured answer compatibility.

Popularity is only a prior. A famous but contradictory candidate should still lose to a less famous candidate that actually matches the player's answers.

## Game personality

The interface reacts to the deduction state:

```text
low signal      -> bro could literally be anybody 💀
mid signal      -> hold up... I'm seeing the vision 👀
high signal     -> nahhhh I might know bro
wrong guess     -> I sold once. It will NOT happen again.
correct guess   -> SUSSY BAKA DETECTED / CAUGHT IN 4K.
give up         -> I'm cooked. 💀
```

These reactions are presentation only. Candidate probabilities and question selection stay independent of the meme layer.

## Getting started

### Requirements

- Node.js 20.9+ (CI uses Node 22)
- npm
- Gemini API key only for Gemini semantic/long-tail recovery
- or a local Ollama model if you prefer local inference

### Install

```bash
npm install
```

Create a local environment file:

```bash
# macOS / Linux
cp .env.example .env.local

# Windows PowerShell
Copy-Item .env.example .env.local
```

### Provider options

#### Mock — zero credentials

```dotenv
AI_PROVIDER=mock
```

The structured candidate/question engine and Wikimedia knowledge discovery still operate. Only the final semantic AI recovery layer uses the mock provider.

#### Gemini

```dotenv
AI_PROVIDER=gemini
GEMINI_API_KEY=YOUR_KEY
GEMINI_MODEL=gemini-3.6-flash
```

The key is server-side only. Never prefix it with `NEXT_PUBLIC_`.

#### Ollama

```dotenv
AI_PROVIDER=ollama
OLLAMA_BASE_URL=http://localhost:11434
OLLAMA_MODEL=YOUR_INSTALLED_MODEL_TAG
```

### Run locally

```bash
npm run dev
```

Open `http://localhost:3000`.

### Full verification

```bash
npm run check
```

Equivalent individual commands:

```bash
npm run typecheck
npm test
npm run lint
npm run build
```

## Security and privacy

- Provider keys exist only in server-side environment variables.
- The browser never calls Gemini, Ollama, Wikipedia, or Wikidata directly for deduction.
- `.env*` files are ignored except the safe `.env.example` template.
- Request bodies are size-bounded and schema-validated.
- Structured model responses are schema-validated again at runtime.
- Raw provider errors, prompts, stack traces, and secrets are not returned to players.
- Duplicate requests for the same in-flight game are rejected.
- Candidate hypotheses remain hidden from the player until an actual guess is made.
- Live knowledge requests use short server-side timeouts and fail open to the local game engine.
- SBD's shared Supabase Project Hub scope is isolated by `SUPABASE_HUB_RULES.md`; persistent learning is not allowed to touch another application's schema.

## Guess confidence policy

SBD does not treat a language model saying `0.99` as a genuine 99% probability.

For structured candidates, game confidence is derived from the posterior distribution, the lead over the runner-up, evidence depth, and uncertainty penalties. For long-tail LLM guesses, self-reported confidence is capped by evidence depth and penalized after rejected guesses. The server guess guard then decides whether the result may be shown or whether another question is required.

Live Wikimedia candidates use an **open-world evidence model**: if a short article extract does not mention a trait, the engine normally treats that trait as unknown instead of assuming it is false.

## Roadmap

The live Knowledge Engine removes the biggest hard-coded coverage limitation. Next steps are deliberately incremental:

- persistent verified entity cache in the isolated SBD Project Hub schema;
- verified learning from legitimate give-up reveals;
- scheduled popularity refreshes for the hottest candidates;
- richer occupation/franchise/team relationships from Wikidata;
- measured Top-1 / Top-3 benchmark suites across thousands of known entities;
- shareable result cards and session stats;
- distributed production rate limiting if traffic requires it.

## Development philosophy

**Quality > quantity.**

The target is not an impossible claim of knowing every human on Earth. The target is a system where most reasonably notable/current people can enter the candidate space automatically, every guess still has evidence behind it, external services can fail without killing the round, and the game stays fun enough that the engineering never feels like homework.
